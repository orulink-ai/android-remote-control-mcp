# 手机录制与 PI Skill 复用：阶段结果

实验日期：2026-10-18（Asia/Shanghai）。正式研究目录为 `artifacts/pi-phone-use/record-replay-20261018-v3/`。本文保留版本演进和验证边界；正式数字仅从 V3 冻结运行产物汇总。

可复核的脱敏指标见 [结果摘要 JSON](phone-record-replay-20261018-summary.json)。它不包含原始账号界面、设备序列号、认证配置或本机绝对路径。

V3 六轮均完成。相同任务的 PI 全程中位数从 Jev 的 22.537 秒降为 Skill 复用的 15.594 秒，减少 6.943 秒（30.8%，速度比约 1.45×）。Skill 每轮模型调用从 14 次降为 0，同时仍完成 9 步验证、5 次条件等待和 1 次确定未派发后的引用刷新。该结果只覆盖当前固定任务与三轮/模式的小样本。

## 本阶段实际实现

手机 App 增加录制入口、开始/暂停/继续/结束、步骤摘要和系统文件导出。电脑端可以把手机事件导入为 Skill 草稿，也可以从真实 PI 成功示教的配对观察生成 `SKILL.md` 与可执行 `recipe.json`。PI 的 `skill` 模式使用相同 Android MCP 读屏、操作和验证，正常步骤只做本地语义匹配，不请求 Jev 或 DeepSeek。

这几项能力应分开理解：

| 链路 | 当前证据与边界 |
| --- | --- |
| 手机录制 → 事件 JSON | 新版 App 已在 Redmi K60 Pro 安装；实际录得 14 个事件，步骤审阅和 Android `CreateDocument` 导出已验证 |
| 事件 JSON → Skill 草稿 | `workflow.py import-android` 生成可读 `SKILL.md` 和 `draft.json`，状态为 `needs-verification`，不能直接作为可执行配方 |
| 成功 PI 示教 → 可执行步骤 | `PHONE_BENCH_RECORDING=1` 保留真实 PI 每个动作的前后观察，成功后由 `workflow.py compile` 生成步骤、来源摘要与配方内容摘要 |
| PI → 复用与验证 | `skill` 模式通过真实 PI、扩展、worker 和策略边界的离线跨进程验证，并在 V3 三轮实机复用中全部通过完整任务验证 |

手机事件草稿与 PI 配对示教是两条不同来源。当前仍需人工发起导出、导入、PI 示教及编译；没有实现 App 内一键把原始事件变成已验证可执行 Skill。`verified-demonstration` 表示示教通过共同观察器，不等于人工已审阅，也不意味着可以适应任意新搜索词、帖子或 App。

产品方向参考 [官方 Record & Replay](https://learn.chatgpt.com/docs/extend/record-and-replay)：演示后整理为包含适用场景、输入、步骤和验证的 Skill，再调用当前环境中的工具复用。本项目在 Android MCP 和 PI 上实现结构化步骤执行，不声称采用官方内部实现。完整交互设计见 [产品方案](../plans/phone-record-replay.md)，运行方式见 [实验模块说明](../../experiments/pi-phone-use/README.md)。

## PI 实际如何执行

```text
PI AgentLoop（phone-benchmark / skill）
  → phone_observe
  → 本地 SkillPolicy 匹配当前语义控件
  → PI phone_action
  → 同一 Android MCP 执行并回读
  → 每步后置条件、最终任务状态验证
```

启动器仍通过 `-e pi-extension.ts` 临时加载自定义 provider，未修改用户 PI 日常默认配置。复用路径中的 `SKILL.md` 是可读说明，配套 `recipe.json` 由专用执行器加载；它不意味着 PI 原生 Skill 引擎会自动把任意文字说明编译成宏。模型判断、语义步骤匹配和调度均在电脑端，手机 App 提供事件、界面状态及执行能力。

`jev` 对照模式在每个决策步骤请求真实 Jev，`skill` 实验模式本地选择动作，两者共享任务阶段、动作边界、手机通道、界面短等待、截图与结果验证。每个任务动作仍由 PI 工具触发。ADB 只用于 USB 传输准备、计时外重置和额外录像，Codex 不替代 PI 做计时内动作选择。

## 任务与共同条件

固定从桌面打开小红书，搜索“小狮日记”，打开同一目标首帖，依次点赞、收藏、取消点赞、取消收藏，最终回读确认两项均未激活。搜索词与目标标题由当前适配器固定，更换输入需重新示教和验证。

V3 两组统一使用 Redmi K60 Pro、Android 16、1440×3200，以及同一构建的 FOSS Debug App。当前截图间隔保护为 350 毫秒，工具指示器保持开启；具体 APK 和 Python/TypeScript 文件摘要由本组运行清单保存。2026-10-17 三星设备与旧版 MCP 的结果不纳入本次统计。

主计时为 PI `agent_start` 至 `agent_end`，包含 MCP 初始化、读屏截图、模型请求或本地匹配、动作、等待、验证、确定未派发时的引用刷新。启动前的 App 冷重置、基线恢复和全部轮结束后的原状态恢复在计时外。示教、生成和额外录像轮单列；不把嵌套的 worker/CLI/网络耗时相加。

## 保守复用而非固定重放

配方保存角色、方法和语义标签，在每次观察中重新解析唯一控件，不保存历史节点 ID 作为长期选择器，也不默认重放历史屏幕坐标。每步绑定任务身份、前置条件和后置条件，步骤与来源摘要随配方保存；修改内容后不能沿用旧验证。

导航和搜索输入后，示教中的 WAIT 被合并为已观察的过渡状态与最终后置条件。快页面直接满足最终条件即可继续；慢页面只在已见过渡状态中等待，单步最多 8 次。每一次等待仍是 PI 工具调用并计时；不重复派发引起加载的原动作。未知界面或预算耗尽时停止。

节点失效与投递异常需要区分以下路径：

- 共同控制器原有的严格 click 重绑定：确认节点查找发生在派发前，且角色、几何、标签、目标身份与状态均一致时，可在同一次 PI `phone_action` 内重绑定一次。Jev 与 Skill 共用此路径，不属于新增配方重试预算。
- 控制器明确返回绑定旧选择与语义意图的 `not_dispatched` 标记，证明**尚未派发任何变更工具**：策略检查当前步骤、任务与前置条件，释放旧引用但不推进步骤，下一次由 PI 重新选择和派发，单步最多 3 次。
- 部分执行、投递不确定、未知状态或矛盾标记：立即停止。即使最终页面碰巧满足条件，也不能据此掩盖投递异常或盲目重复点击。

当前 `skill` 漂移策略为停止。现有独立 `jev-auto` 模式可以在确认现状后重新运行，但本阶段没有自动把 Jev/DeepSeek 的恢复动作接回配方。产品原型中的可变参数、浮条、编辑器和自动恢复属于后续完整体验。

## 为什么保留 V1、V2

每次影响读屏节奏或执行协议的修复之后，完整对比必须重新开始。旧轮保留诊断价值，但不能拼入 V3，或选取其中成功结果替换 V3 的失败。

| 版本 | 已保留记录 | 中止原因与处理 | 是否进入 V3 |
| --- | --- | --- | --- |
| V1：`record-replay-20261018` | `rr-r1-jev` 成功；`rr-r1-skill` 在 MCP 工具调用报错后停止；早期示教和 warmup 均保留 | 实测发现截图间隔保护问题；修正共同截图请求节奏后重新示教、重开一组 | 否 |
| V2：`record-replay-20261018-v2` | `rr-r1-jev` 成功；`rr-r1-skill` 在策略后置条件检查时停止 | 搜索输入首个清空请求遇到明确未派发的旧节点引用，返回新观察后被当成已执行动作验证；以 TDD 增加严格未派发协议后重开一组 | 否 |
| V3：`record-replay-20261018-v3` | 独立示教、固定六个正式 ID 和两个额外录像 ID | 冻结共同控制器、配方与 PI 桥接，再从相同基线完整比较 | 正式组 |

其他诊断修复也保留其作用范围：只有真正聚焦桌面才提供 `OPEN_APP`，系统窗口独占的短暂页面切换作为过渡界面等待；一次性提示不默认当作稳定流程的一部分。旧示教的存在不证明当前配方来源，最终报告通过 `sourceDemoTrialId` 显式绑定实际采用的示教轮。

V1/V2 是开发过程中发现实现问题后中止的版本，不是当前版本全部任务的失败率样本，也不能与 V3 合并后计算更好看的成功率。它们同样不能被隐去后宣称本功能第一次就成功完成。

## V3 正式结果

以下由 V3 的六个预设正式 ID 汇总。两组成功率均为 3/3；额外示教、录像和 V1/V2 均不进入此表。

| 正式轮次 | Jev PI 全程 | Skill PI 全程 | 结果 |
| --- | ---: | ---: | --- |
| `rr-r1-jev` / `rr-r1-skill` | 22.537 秒 | 15.523 秒 | 两组成功 |
| `rr-r2-jev` / `rr-r2-skill` | 21.823 秒 | 15.769 秒 | 两组成功 |
| `rr-r3-jev` / `rr-r3-skill` | 23.563 秒 | 15.594 秒 | 两组成功 |
| 成功轮中位数 | **22.537 秒** | **15.594 秒** | **耗时减少 30.8%** |

每个 Jev 轮均有 14 次有效模型响应 / 14 次请求，每个 Skill 轮均为 0 / 0。Skill 每轮验证 9 步、条件等待 5 次、引用刷新 1 次，共产生 10 次步骤匹配选择；其中引用失效的一次没有派发变更工具，不是重复执行点赞或收藏。Jev 每轮调用共同读屏工具 16 次，Skill 为 17 次；本轮加速没有通过减少这一计数来获得。

中位数只取成功轮，失败保留在成功率分母。本轮正式六个样本全部成功，不代表长期 100% 成功率。少于两次有效成功或六轮不全时，报告不会发布加速收益。

V3 采用本组独立的 `demo` 为配方来源，示教耗时 23.406 秒，生成并写入 9 步技能包约 1.220 毫秒；最终计时文件自身写入不包含在生成指标内，人工审阅耗时未知。按每轮节省 6.943 秒估算，仅生成耗时在 1 次复用内回收；把完整示教耗时一并计入约需 4 次。该估算不包含未知人工时间，不等同于一般任务的成本承诺，也不能用毫秒级编译时间掩盖一次完整示教。

## 录像、界面证据和局限

最终报告内嵌独立录像轮，1 倍速、不剪掉等待或恢复；视频起止包含少量计时外画面，时长与 PI 计时分别展示。录像轮不进入正式三轮统计。App 实机准备页、步骤审阅和导出截图独立展示，与可操作产品原型分区。

| 主录像轮 | PI 全程 | 原速视频时长 | 结果 |
| --- | ---: | ---: | --- |
| `video-jev-retry-1` | 24.642 秒 | 26.740 秒 | 六阶段完成 |
| `video-skill` | 17.086 秒 | 19.238 秒 | 六阶段完成 |

额外首次 `video-jev` 在打开目标帖阶段后选择 `BLOCKED` 并停止，最终点赞、收藏均未激活；这次失败录像与元数据原地保留，不覆盖或剪接。重新录制使用独立 `video-jev-retry-1` 与新文件名，报告通过显式 `video-selection.json` 选择主视频，同时展示较早失败状态、原因和原始录像入口。正式六轮仍全部成功，但不能据此隐去录像轮的失败。

最后 `video-skill` 的任务内最终回读已确认未点赞、未收藏，该完整结果验证包含在 PI 计时内。收尾时对照本组开始前记录，确认原始状态也为两项未激活，因此无需额外切换操作；收尾对照不另计入测速。

最终 HTML 已完成桌面和 390 像素移动视口检查，无页面横向溢出。两条主视频元数据加载、画面解码、1×同时播放及一起暂停通过；保留的失败原片入口可打开。正式表仅六轮，每轮和两条成功主录像均包含六个完成阶段。三张 App 实机图均成功加载；录制、暂停、审阅、参数、运行和结果原型可交互，且与实机证据及人工配对验证边界明确分区。QA 截图保留在本地报告目录，未把浏览器截图作为新的手机操作或测速证据。

目前不以离线协议测试代替实机性能结果，不把已安装 App 或导出成功等同于自动完成验证，不对任意 App、搜索结果或屏幕布局作泛化承诺。截图颜色验证器和专用任务适配仍有几何、语言及页面结构约束。三轮/模式是小样本，页面缓存、加载与网络变化会影响结论。
