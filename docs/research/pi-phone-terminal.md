# pi-phone 终端入口：实际控制链路与验收记录

日期：2026-10-18（Asia/Shanghai）。本文归档入口核查、已安装的新链路和分阶段实机证据。当前已验证入口身份、实时读屏、打开应用、普通换词搜索，以及录制命中和漂移后的完整闭环。受控 Jev 失败后的真实 DeepSeek 兜底也已通过一轮实机验证，早期失败全部保留；不以旧专用测试结果代替本页验收。

## 为什么专用测试有效，普通 pi-phone 却没有使用同一条链路

此前存在两个不同入口。研究代码已经跑通，并不表示日常终端命令已经启用它。

| 核查项 | 此前专用实验 | 修改前的普通 pi-phone |
| --- | --- | --- |
| PI 启动 | 启动器显式 `-e pi-extension.ts` | 本地包装命令直接启动 PI，只追加手机控制提示词和 MCP 工具范围 |
| Provider / model | `phone-benchmark`，显式选择 `jev`、`skill`、`skill-auto` 等模式 | 包装命令未指定模型，沿用 PI 默认 `deepseek` / `deepseek-flash` |
| 手机工具 | 扩展的 `phone_observe` / `phone_action`，再调用本项目 MCP | PI 原生暴露的 `watcher_android` MCP 工具 |
| 已录制流程 | 显式配置 `recipe.json`，由专用执行器加载和验证 | 未安装或选中对应的流程接入；没有把请求路由到配方执行器 |
| 任务约束 | 固定搜索词、目标首帖、阶段目标、候选过滤与结果验证 | 普通对话任务，由默认模型根据 MCP 返回值逐步规划 |
| 实验数字说明什么 | 该专用模式下的全流程耗时与完成证据 | 不能据此认定普通入口也在使用 Jev 或命中 Skill |

修改前的包装命令只把工具限制为 `mcp__watcher_android__*`，并追加手机控制提示词；它没有加载手机决策扩展，也没有选择 Jev。提示词本身还明确要求使用 PI 当前配置的模型，不能宣称自动启用 Jev 或 Skill。核查时 PI 默认确实为 DeepSeek Flash。

因此，普通 pi-phone 的表现不能被解释成“Jev 已经接入但变慢”或“录制 Skill 没有收益”。当时普通入口根本没有走专用测试链路。此前若把“实验扩展已接 PI”概括成“日常 pi-phone 已接好”，这个说法范围过大，应以本次入口修正和下方验收为准。

电脑上存在 `SKILL.md` 或 `recipe.json` 也不等于正在执行该流程。前者是可读说明，后者是执行器使用的结构化步骤；还需要正确入口、明确选择、当前任务匹配，以及逐步验证。PI 原生读取一段 Skill 文字，与这里的本地配方执行器，是两种不同机制。

## 用户如何从终端开始

这份步骤针对本机已安装的新包装命令。换一台电脑时，需要先配置同样的入口与依赖，不能把仓库里有实验源码当成已安装。日常使用无需运行旧 benchmark 的 ADB 转发、force-stop 或录像脚本。

1. 在手机启用本项目无障碍服务并启动 MCP 服务，手动解锁，保持亮屏；电脑与手机能访问配置中的 LAN HTTP 服务。
2. 退出此前的旧 pi-phone / PI 进程，重新在终端运行 `pi-phone`。普通 `pi` 仍是普通入口，不会因为本次安装就自动切换到新手机链路。确认当前 provider / model 为 **`phone-control / auto`**。如果仍显示 DeepSeek 默认聊天模型，先排查启动入口，不继续声称已经使用 Jev。
3. 在 PI 中输入 `/phone-status`。它显示决策路径、当前配方和支持范围；显示配置成功不是业务任务已经执行。
4. 输入 `读取当前手机屏幕`。若结果提示锁屏，先手动解锁；这一步通常没有模型请求，验证的是实时读屏通道。
5. 输入 `打开小红书`。以实际前台包名和结果验证为准。应用已在前台时允许直接确认完成，不需要再制造一次打开动作。
6. 输入 `小红书搜索“小狮日记”，停在搜索结果页`。这属于普通搜索路径，不会因为词与录制配方相同就自动点赞或收藏。
7. 需要完整复用时输入 `/phone-replay`。该命令明确授权固定搜索词、固定首帖、点赞、收藏、取消点赞、取消收藏的完整闭环。运行前记录目标帖原状态并满足配方基线，运行后核验；失败后先读屏，不盲目重复该命令。

以下是在同一 PI 会话内逐条输入的示例，最后一行才是会改变帖子状态的录制闭环：

```text
/phone-status
读取当前手机屏幕
打开小红书
小红书搜索“小狮日记”，停在搜索结果页
/phone-replay
```

精确输入 `/skill:xhs-recorded-roundtrip` 也是同一个固定闭环入口，可替代 `/phone-replay`。扩展在 input event 阶段把这个**完整且无参数的别名**规范化为“执行录制的小红书完整闭环”，然后走相同的授权路由和 `recipe.json` 验证。它不是把任意 `SKILL.md` 文本当代码执行，也不是 PI 原生 Skill 引擎自动理解任何新步骤。别名不支持附加搜索词、帖子或其他参数；需要变化输入时，本阶段应拒绝，参数泛化仍由 issue #5 跟踪。

自然语言完整授权也只接受已覆盖的明确正向表达，例如“执行录制的小红书完整闭环”。否定、咨询、第二篇帖子、额外评论或发布请求不能触发这个固定流程。不要用一段解释性文字或“不要执行……”尝试替代明确命令。

### 配置在哪里查看

启动器通过 `PI_PHONE_PROFILE` 指定的本机 profile，默认引用 `~/.config/orulink-phone/terminal.json`。这里只列配置引用，不公开真实手机地址、鉴权 headers、密钥或账户数据。

| 配置项 | 用途 | 检查原则 |
| --- | --- | --- |
| `pi` / `python` | PI CLI 与 Python 运行时；Python 必须为绝对路径 | 使用与扩展兼容、安装了依赖的环境 |
| `mcpConfig` / `mcpServer` | 引用私有 MCP 配置与 `watcher_android` server | 启动器读取该 server 的 HTTP URL，OwnMcp 读取对应鉴权；不复制配置到聊天或报告 |
| `recipe` | 当前已验证的固定 `recipe.json` | 内容摘要、任务身份和结构必须通过加载校验；参数变化不沿用旧验证 |
| `keyFile` | OpenRouter 私有密钥文件引用 | 不把密钥写进命令参数；本地流程命中无需模型调用 |
| `output` | 本机终端任务记录目录 | 每次用户任务使用独立 trial；需要分享时只提取脱敏字段 |

`/phone-status` 可以帮助确认当前配方引用，但不会把配置加载或模型列表当成任务成功。检查本机配置时不要粘贴完整文件内容。

### 常见问题怎么定位

| 看到的现象 | 对应层次 | 下一步 |
| --- | --- | --- |
| 界面仍显示默认 DeepSeek 模型 | 命令 / provider | 退出旧进程，确认正在运行新 pi-phone 包装命令；不要在 benchmark 和普通入口之间混读日志 |
| pi-phone 报配置无效，尚未操作手机 | 本机 profile / 配方 / 运行时 | 核对上述文件引用与依赖，不把密钥或 URL 发到报告 |
| `/phone-status` 没有当前配方或命令不存在 | 扩展加载 / 配方引用 | 确认 `terminal-extension.ts` 与 `phone-control / auto`，检查是否仍在旧会话 |
| 读屏成功，但结果为锁屏 | 手机状态 | 手动解锁后重新观察；不能把锁屏读屏成功当作可以控制小红书 |
| 应用列表找不到小红书 | MCP 应用可见性 | 列表可能受 Android 限制；当前实现可用已知别名或明确包名作为候选，最终仍看实际前台验证 |
| 小红书本来就在前台却停止 | 状态判断 / 旧代码 | 当前实现应先核验唯一目标是否已在前台；保留旧失败记录，确认已启动更新后的入口 |
| 短暂没有 focused window | 手机页面过渡 | 当前实现只做有界的等待与重新读屏；不因为短暂缺焦点而重复派发打开动作，持续无法确认则停止 |
| 搜索词正确但任务未确认完成 | 通用搜索适配 / 页面状态 | 查看是否进入搜索结果页及前台是否正确；不要手动点赞来“帮助完成”普通搜索 |
| 完整流程没有命中配方 | 任务授权 / 固定范围 / 当前状态 | 使用精确 `/phone-replay` 或无参数别名，核对固定词、首帖与基线；不要把新目标默认为旧配方 |
| Jev 请求失败后出现一次新的观察 | 模型回退 | 这是 DeepSeek 兜底前的状态刷新；是否最终成功看后续轨迹和验证，不只看模型名称 |
| MCP 动作后报错或投递不确定 | 执行 / 验证 | 先读屏确认，停止并保留记录，禁止盲目重放点赞收藏 |
| 出现 ADB 要求或需要设备序列号 | 入口混用 | 停止使用旧 benchmark 启动命令；新日常入口通过已配置 LAN MCP，不需要 ADB 准备 |

## 本次统一入口的接入约定

日常 pi-phone 已安装为新终端启动器，由 `phone-control` provider 的 `auto` 模式承担统一入口。当前实现的加载链路如下；每个任务是否成功仍需分别查看本页运行记录。

```text
用户终端 pi-phone：自然语言任务
  → terminal_launcher.py
  → terminal-extension.ts
  → 同一 PI 会话 / AgentLoop：phone-control / auto
  → worker：terminal-auto → Python 任务路由器
      ├─ 匹配已验证的固定录制任务 → skill-auto
      │    ├─ 当前步骤命中 → 本地语义选择，0 次模型 API
      │    └─ 可恢复漂移 → 本轮剩余任务交给 Jev
      │         └─ Jev 请求失败 → PI 显式重新观察 → DeepSeek 兜底一次
      └─ 支持的普通任务 → 通用 jev-auto
           └─ Jev 请求失败 → PI 显式重新观察 → DeepSeek 兜底一次
  → PI phone_observe / phone_action
  → OwnMcp → 本项目 Android Remote Control MCP（LAN HTTP）
  → 手机无障碍服务执行、读屏与结果验证
```

模型和任务选择发生在电脑端；手机 APP 提供本项目 MCP 服务、无障碍状态和执行能力。这里没有切换到另一个项目的 ADB 手机服务，也不需要由 Codex 替代 PI 选择计时内动作。

新启动器显式加载 `terminal-extension.ts`、选择 `--provider phone-control --model auto`，只暴露 `phone_observe,phone_action`，并关闭原生 MCP 工具加载。Python worker 内部再选择 `jev-auto` 或 `skill-auto`。因此外层 PI 当前模型显示 `auto`，不意味着底层每步使用同一个模型；是否请求 Jev、是否命中流程，应读取实际策略记录。

连接地址来自用户既有 `watcher_android` 的 HTTP 配置，当前实测采用 Wi-Fi LAN URL；鉴权留在私有配置中。终端路径不调用旧实机 benchmark 启动器的 ADB 冷重置或 screenrecord。仅加载 provider、启动会话成功，或在模型列表中看到 Jev，都不足以证明某个任务已经通过它完成。

### 本地命中、模型恢复与停止条件

- 流程命中使用当前观察中的语义控件，验证每步前后条件；0 API 指没有请求模型，MCP 观察、动作、等待和验证仍然发生并计时。
- `skill-auto` 仅对支持的可恢复界面漂移切换到 Jev；不把模型恢复动作强行接回旧配方步骤。当前任务身份不符、歧义目标、预算耗尽、部分执行或投递不确定时应停止。
- Jev 请求失败发生在动作派发前。DeepSeek 必须基于 PI 新一次 `phone_observe` 的观察尝试一次，不能直接执行旧观察中的选择；后续步骤按实际策略重新决策。
- MCP 动作超时或断连可能已经改变手机。不能用换模型或盲目重复点赞、收藏来“重试”；应先核验，交付不确定的动作停止。
- Jev 与 DeepSeek 当前均经 OpenRouter。模型回退不保证能绕过共享网络或网关故障。

## 当前支持范围

统一入口不等于已经完成任意 phone use。

| 任务类型 | 本阶段范围 | 不应宣称的能力 |
| --- | --- | --- |
| 普通读屏 | 读取当前手机界面 | 读屏成功不等于业务任务完成 |
| 普通打开应用 | 按可见应用列表、已知小红书别名或明确包名提供候选；实际打开后核验前台包名 | 应用列表不可见不等于应用未安装；能打开不等于支持其任意工作流 |
| 普通搜索 | 在小红书内执行请求的搜索并核验 | 搜索完成不等于已支持点赞、评论或发布 |
| 录制流程复用 | 已验证的固定搜索词、固定目标首帖、点赞收藏及取消两项闭环 | 不自动适配新搜索词、新帖子、新账号或新布局 |
| 参数泛化 | issue #5 跟踪，尚未实现 | 不把替换一句自然语言输入当成配方已泛化 |

不匹配已验证流程的请求，不能为追求“命中 Skill”而偷偷换成固定搜索词或目标帖。属于普通任务的请求应进入相应通用路径；尚不支持的动作应明确报告范围，不能伪装成完成。

手机原始无障碍录制的导出仍是待验证草稿。它与从成功 PI 示教生成的已验证配方需要分别标明来源；终端入口统一不意味着“App 任意录一遍就自动生成可靠配方”的产品流程已经完成。

## 每次运行需要分别展示的事实

| 字段 | 应记录的证据 | 不能混用的概念 |
| --- | --- | --- |
| PI command | 实际执行的包装命令、加载的扩展和显式 provider / model 标志；不含密钥 | 命令名叫 pi-phone 不代表内部一定选了 Jev |
| Provider / model | 外层 `phone-control / auto` 与每次真正采用的 backend 分开 | 外层 auto 名称不等于每一步都请求模型 |
| PI session | 本次会话标识、工具轨迹与最终结果，报告中使用相对文件名 | 历史成功会话不能证明当前任务已完成 |
| Transport | 本项目 OwnMcp、MCP 服务身份、LAN HTTP；敏感地址和鉴权信息不公开 | 使用 Jev 不意味着使用另一个项目的 MCP 或 ADB |
| Recipe | 是否匹配、配方摘要、来源示教和选择原因 | 配方存在不等于已安装、选中或执行 |
| Execution | 路由类型、命中步数、模型调用数、漂移、回退与验证结果 | 本地步骤命中次数不是模型请求次数 |

用户应该能看出本次到底是“录制流程命中”“通用 Jev”“Jev 后 DeepSeek”，以及失败发生在路由、模型请求、MCP 还是结果验证。既不能把 DeepSeek 原生 MCP 会话称为 Jev，也不能把流程的本地选择称为模型判断。

### 模型回退与外层 PI 重跑是两层机制

内部决策回退是 Jev 请求失败后，通过 PI 显式重新观察，再尝试 DeepSeek 一次。`terminal-18de8944` 已证明该顺序以及 DeepSeek HTTP 429 后无动作停止；随后使用独立新 ID `terminal-e32ca43c-f40a-4614-a79d-cbe633fd76d9` 完成真实兜底。

成功故障轮 PI 全程为 **5,955.818834 毫秒**。PI 工具顺序是 `phone_observe` → `phone_observe`（回退刷新）→ `phone_action`（DeepSeek 选择 OPEN_APP）→ `phone_action`（Jev 选择 WAIT），最后确认小红书处于前台。策略记录包含三次尝试：

| 次序 | 请求类型 | 结果与时延 |
| --- | --- | --- |
| 1 | Jev 受控故障，尚未发 HTTP | 注入 ConnectError，约 0.470 毫秒；不是一次真实模型响应 |
| 2 | 真实 DeepSeek HTTP | `deepseek/deepseek-v4.1-flash`，成功，1,658.113 毫秒 |
| 3 | 真实 Jev HTTP | `typesafe/jev-1.14-20261014`，成功，1,113.599 毫秒；等待后验证目标前台 |

因此这是三次策略尝试、两次真实模型 HTTP 请求，不应将注入故障也算成真实模型调用。该轮只验证打开任务中的回退，不代表在真实未知副作用之后可以安全重放动作。

为了尝试同一 DeepSeek 型号的其它 OpenRouter 供应商路由，本次只在新 terminal 模式启用 `allow_fallbacks=True`；旧 benchmark 仍默认 `False`，不能把这项变化混入旧实验。成功轮说明启用该路由选项后这一轮能完成；没有证据表明网关内部实际尝试了几个供应商，也不能证明此前 429 已被永久解决。这里的 OpenRouter 供应商回退与应用层“Jev → DeepSeek”是不同层次，不能合并为一个回退次数或性能结论。两者也不能保证解决共享网络或网关故障。配置语义参见 [OpenRouter 官方供应商路由说明](https://github.com/OpenRouterTeam/docs/blob/main/guides/routing/provider-selection.mdx)。

此外，真实 PI 测试发现：如果把手机业务失败包装成外层 model 的 `stopReason:error`，PI 可能自动重跑整个用户目标，而不只是重试一次模型请求。离线真实 PI 测试已先复现重复 `observe/decide/finish` 直至超时，再修为 terminal 业务失败输出正常 `stop` 和明确失败文字；底层 trial 仍为 `failed`，不会伪装成任务成功。取消仍按 aborted，旧 benchmark 的错误协议不变。

因此，正常返回的终端文字可能是“任务失败，已停止”。应同时核对文字、trial 状态和副作用轨迹；不能把 RPC 正常结束或 `stop` 当成业务成功，也不能依靠外层 PI 自动重跑手机操作。该缺陷通过实际 PI 的超时/重复命令测试先复现，修复后对应 8 项边界测试通过，其中实际 PI 验证约 1.65 秒有界结束；这些测试使用替身，不额外操作真实手机。

最后一次实际命令任务为 `terminal-56464043-7ef1-4158-b858-195c9719a069`，PI 全程 23,791.525041 毫秒。`verifiedSteps=5/9`、`recipeHits=8`、`settleWaits=1` 和 `recoveryActive=True` 如实保留；模型为 Jev 5 次，完成来自配方与模型恢复共同推进，不能用“命中 8 次”冒充“验证 8 步”。

最后回读确认目标帖 `liked=False`、`collected=False`、`firstTitleVisible=True`、`locked=False`。两项账户状态与终端实验最初保存的 `original-post-state.json` 一致，不需要额外切换恢复；之后未再操作手机。该原始状态对照核验与单轮任务计时分列，早期失败轮未触发账户副作用。

### 继续验收时必须保留的区分

- 路由器必须先确认请求授权和范围，再初始化手机；不要把“询问流程”“不要执行”或另一篇帖子的请求匹配成固定完整 Skill。
