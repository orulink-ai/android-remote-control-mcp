# PI 驱动 Android MCP：Jev / DeepSeek 阶段实验

实验日期：2026-10-17（Asia/Shanghai）。阶段归档日期：2026-10-18。精简证据见 [JSON 结果](pi-phone-use-20261017-results.json)。

这次固定手机任务中，Jev 成功轮更快：成功轮 PI 耗时中位数 28.69 秒，DeepSeek 为 39.77 秒。但 Jev 正式完成 2/3，DeepSeek 完成 3/3；样本很小，且一次 Jev 连接失败未得到模型响应，不能据此推出模型普遍速度或可靠性排名。适合作为下一阶段“Jev 优先、DeepSeek 决策失败兜底”的依据，自动回退尚未实现。

## 当前接入 PI 的形式

已经通过真实 PI 1.3.0 的 AgentLoop 跑通，但接入形式是实验专用 extension，而不是安装另一个手机 MCP。启动命令通过 `-e pi-extension.ts` 临时加载扩展，注册自定义 `phone-benchmark` provider，选择 `jev` 或 `deepseek`，并提供 `phone_observe`、`phone_action` 两个工具。

```text
PI AgentLoop
  → phone_observe / phone_action
  → Python NDJSON worker：共享状态、候选与任务阶段
  → OpenRouter：Jev 或 DeepSeek 选择动作
  → 本项目 Android MCP：执行、读屏
  → 共同验证器 → 下一轮 PI 决策
```

具体来说，provider 将真实模型返回的结构化选择转为 PI 工具调用；PI 驱动逐步的 observe → decide → act → observe。Python worker 持有模型 HTTP client 与 MCP 会话，Android APP 提供无障碍树和执行能力。模型选择发生在电脑端。

本阶段为固定的“小红书搜索、打开首帖、点赞收藏、取消两项”任务提供阶段目标、候选动作和验证逻辑。它还不是接收任意自然语言任务的通用自主 phone agent，也没有注册到用户日常 PI 默认配置。计时期间的任务动作由 PI 工具触发；Codex 负责实验准备、运行与计时外恢复。ADB 用于 USB 转发、计时外启动基线重置和录像。

## 任务、版本与共同条件

- 从 Android 桌面开始，打开小红书，搜索“小狮日记”，打开当时第一篇帖子，依次点赞、收藏、取消点赞、取消收藏，回读确认最终两项均未激活。
- PI：1.3.0；手机 Android：16；实际已安装 Android Remote Control MCP：1.12.0，并非当前源码 HEAD 重新构建。
- Jev 请求模型为 `typesafe/jev-1.14`，实际返回为 `typesafe/jev-1.14-20261014`；DeepSeek 请求和实际返回均为 `deepseek/deepseek-v4.1-flash`。
- 两模型均经 OpenRouter，使用同一手机、MCP、USB 通道、共同阶段目标、精简状态、候选动作、执行器和验证器。Jev 使用一次请求的 operation/target heads；DeepSeek 关闭 reasoning，以 JSON 选择候选。模型适配协议不同。
- 所有正式轮采用会话内持久 HTTP/2 client。每个会话的首请求仍可能新建连接，连接、TLS 和网络等待都计入耗时。
- 父子可点击候选去重，只有明确未派发动作的失效节点才按角色、标签、位置与当前状态重新绑定。界面等待、重读与恢复都计时；不对模型失败自动重试或切换模型。
- 视频图标的点赞状态缺少可靠语义标记，使用两模型共用的截图固定区域颜色验证器；截图和验证计入任务时间，截图没有交给模型进行视觉判断。当前仍有共同的 400/600 毫秒等待，并非完全事件驱动。

主指标是 PI `agent_start` 到 `agent_end`，包括 MCP 初始化、观察、请求、动作、界面等待和验证。轮前冷重置与基线清理在计时外；CLI、worker 和网络分段是嵌套指标，不能相加。正式顺序为 Jev、DeepSeek / DeepSeek、Jev / Jev、DeepSeek。

## 两类失败需要分开处理

`final-r3-jev` 已完成 MCP 初始化与读屏，手机仍在桌面。首次模型请求约 6.47 秒后失败；TCP connect 约 4.85 毫秒，没有观测到 TLS 完成、HTTP 响应或有效模型选择。缺失网络分段保留 `null`，不填零。

这说明请求没有产生可执行决策，但不能确定具体原因。实验日志把底层异常统一包装为“请求失败或响应无效”，丢失原始异常类型，无法区分本地链路、TLS、网关或远端关闭连接，也不能据此认定 Jev 模型本体不稳定。归档版已增加脱敏后的异常类型和请求阶段；历史失败的底层原因仍无法补回。

该轮之后的轮间清理另遇到 MCP `503 Too many active sessions`，当时达到 100 个活动会话。实验客户端关闭 TCP 时没有发送 MCP 会话 DELETE，导致累积；清理本实验明确掌握的会话后继续。这是轮间客户端会话生命周期问题，独立于模型 API 失败，不计为 Jev 判断失败。归档版已补 DELETE、幂等关闭和初始化失败清理的离线回归测试，长期实机稳定性仍待验证。

## 几百毫秒与整段任务时长

优化后的正式 Jev 请求确实出现约 488～645 毫秒的读屏后决策响应；也存在超过一秒的请求。API 总耗时包含网络、连接、网关排队和服务端处理，不是纯 GPU 推理耗时。`requestToHeadersMs` 同样混合这些等待，connect 包含 DNS 与 TCP，无法再单拆 DNS。

另做真实手机状态的 PI 只读回放：从同一正式轮选取 6 个实际观察，cold / warm 对应请求的 payload SHA-256 完全一致，模型同为 Jev。每组固定推进 6 个快照，不派发手机动作，也不根据选择正确性判定完整任务成功。

| 回放策略 | PI 总耗时 | 单请求中位数 | 实际协议 |
| --- | ---: | ---: | --- |
| cold：每次新 client | 15.107 秒 | 2.630 秒 | HTTP/1.1 |
| warm：持久 client | 8.887 秒 | 1.227 秒 | HTTP/2 |

warm 首个新连接请求保留在统计中。这里同时改变协议和连接策略，只能说明二者联合条件下的差异，不能单独归因为连接复用。与早期原型的历史比较还同时改变了状态精简、候选去重、Jev heads 和恢复策略，也不支持单项因果结论。其他团队的浏览器、直连、地域与模型版本结果亦不能直接当作本机 phone use 的目标保证。

## 验证、状态恢复与下一阶段

原实验的 42 个离线测试通过，包括 provider/网络 trace、候选去重与节点绑定、只读回放、真实 PI 加 fake decision 的协议烟测，以及录像进程归属与文件验证。阶段归档时已重跑这 42 项；它们不发起真实模型请求或手机动作，不替代上述实机六轮证据。精简 JSON 保留冻结实验运行文件的 SHA-256，避免将后续修改误认为当时测速版本。

归档到 [`experiments/pi-phone-use/`](../../experiments/pi-phone-use/README.md) 时，另做了可移植配置、MCP 会话 DELETE 与初始化失败清理、脱敏异常类型和阶段记录、重复动作计数修复，以及任务失败的 CLI 非零退出和空末态报告处理。归档版共 **94 项测试通过**（`python -m pytest -q experiments/pi-phone-use`），Ruff 格式与静态检查、Python 编译检查和报告 JavaScript 语法检查通过。离线 PI smoke 使用真实 PI 和假模型，不连接手机。Android APP 源码未改动，本阶段不重新构建 APK；归档版未重新进行实机测速，不覆盖原冻结版本的结果。

实验最初目标帖状态为“已点赞、未收藏”。正式轮与录像轮的任务基线为“两项均未激活”，每个成功轮结束也回到此状态。全部手机实验后，已在计时外恢复并核验为最初“已点赞、未收藏”，恢复不计入模型耗时。

建议下一阶段实现 Jev 优先与 DeepSeek 决策失败回退，但本阶段尚无自动 fallback：

1. Jev 超时、连接失败或返回非法候选，且动作尚未派发时，以同一最新状态和候选交给 DeepSeek；记录原始失败、回退模型、额外时长与最终结果。
2. 状态已过期则先重新观察；两个模型都失败时有界结束，不无限重试。
3. MCP 动作超时、断连或交付不确定时，先读屏确认。点赞和收藏是 toggle，盲目重放可能抵消已经完成的动作；换模型也不能替代动作核验。
4. 两模型共用 OpenRouter；共享网络或网关故障下，DeepSeek 回退也可能失败。下一阶段应单独测试回退路径、共享故障和会话长期运行，再决定是否增加独立推理入口。

这份交付归档固定任务的可复核证据与实验边界；通用任务接口、默认 PI 安装和自动回退属于后续实现范围。
